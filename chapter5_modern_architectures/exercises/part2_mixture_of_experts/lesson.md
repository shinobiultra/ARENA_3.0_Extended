# 5.2 — running the inline MoE lesson from a completed copy

The exercise notebook remains the lesson. Its21 core methods, immediate tests, matched training,
controls, signature and play cells remain inline. This entry point supplies source preparation and
execution records; it does not implement the MoE methods or certify mastery.

There are two distinct ways to obtain a completed source copy:

- Complete the exercise functions yourself in a separate notebook. Different algorithm bodies and
  reviewed mathematical imports are supported. The validator freezes your actual submitted bodies;
  it does not require them to match the worked answers.
- Explicitly request public-reference preparation. This fills a new copy from the notebook's own
  public Solution blocks. It is exposed reference practice and says nothing about student authorship
  or unseen assessment. Preparation executes no notebook cells or method code.

Execution accepts an already completed copy. It never fills stubs, replaces the input file or
silently borrows generated solution implementations.

## Source-only commands

From the repository's existing Python environment:

```bash
uv run --no-sync --offline python chapter5_modern_architectures/exercises/part2_mixture_of_experts/execute_learner.py --check
```

CHECK is the default. Importing the module or running CHECK uses only Python's standard library:
JSON, AST, source hashes and compilation without execution. It does not import torch/NumPy,
load a model, start a kernel, run a test/method or change a notebook.

To deliberately prepare an exposed public-reference copy in a **new** directory:

```bash
uv run --no-sync --offline python chapter5_modern_architectures/exercises/part2_mixture_of_experts/execute_learner.py --prepare-reference --output-dir /tmp/moe-reference-practice
```

The new `public_reference_practice.ipynb` retains every original nonanswer cell, its tests, order,
metadata and saved output objects. Only the21 declared implementation occurrences change.
`preparation_receipt.json` records `executed:false`, exposure and `authorship:not_inferred`.
An existing directory is refused. No figure or numerical result is produced. Relative output directories are resolved
against the caller's working directory before any files or runtime paths are created.

To check your already completed copy without executing it:

```bash
uv run --no-sync --offline python chapter5_modern_architectures/exercises/part2_mixture_of_experts/execute_learner.py --validate-completed /absolute/path/to/my_completed_copy.ipynb
```

Your input is read, never rewritten. The validator binds the actual answer source and signatures,
fixed experiment/test source, order, metadata and frozen dependencies. Runtime execution counters,
outputs, execution/trust metadata and newly assigned cell IDs may differ in a private copy;
Python language-version metadata may also change. These exceptions do not change experiment code.
The original canonical notebook objects remain untouched.

## Explicit execution boundary

The implementation has an explicit `--execute /absolute/path/to/completed.ipynb --output-dir NEW_DIR`
branch. It starts a real `NotebookClient.execute` only after validating and snapshotting that
completed copy. There is no automatic completion, kernel launch or scientific callback from CHECK,
validation, reference preparation or module import. The current source engineering did not run this
branch with a real kernel; any target run needs its own execution authority.

The completed copy and source snapshots are preserved before execution. Known local dependencies
are copied at their original relative paths into `NEW_DIR/source_snapshot`. The kernel's cwd and
explicit local import prefixes point there, so the unchanged notebook discovers that isolated root
and its generated figure stays beneath the new run. No historical signature image or report is
copied into the workspace: the display cell must consume the fresh figure generated by its own
CPU experiment. This protects the fixed notebook's output paths; it is not a sandbox for arbitrary
submitted Python.

This is the existing CPU notebook protocol, including180 steps, seeds7/19/31, fixed train/dev/final
roles, existing assertions, printed negative specialization verdict and original play. No method,
cohort, metric, default, predicate or measurement is changed. The separate existing strict CUDA
release functions remain exactly as they were; this tool adds no compulsory GPU run.

A submitted-copy execution uses `authorship:not_inferred` and exposure unknown. `--reference-practice`
can explicitly label a supplied public-reference copy. Neither label infers student authorship.
Only after the runtime returns and every nonempty code cell has an execution count without errors
can the receipt say `execution_completed:true` and `completed_from_supplied_answers:true`. It still
says `scientific_acceptance:false`. On a runtime or validation failure it retains the submitted bytes,
actual answer binding and a FAILED receipt; any partially executed notebook returned by the kernel
adapter is kept. Reruns require a new output directory.

## Supported source layouts and limits

The frozen contract binds all94 source cell objects, each specific stub occurrence/interface, its
own visible worked answer bytes and seven local source files. Class method occurrences and duplicate
function names in different cells are separate. A nearest unambiguous source occurrence selects a
public answer; missing or ambiguous mappings fail closed. One existing published interface variant
is recorded explicitly: `SparseMoETransformer.greedy_generate` has an inference-mode decorator in the
worked answer that is absent in its stub. Argument names/defaults remain identical.

Learner bodies may differ. Nested algorithms, local variables and declared mathematical imports are
supported. Existing class method sets/order and declared call interfaces remain fixed; an extra sibling
method or unsupported layout needs review rather than silent acceptance. New nonanswer statements,
changed immediate tests/defaults, remaining stubs, unreviewed body imports, explicit generated-solution
imports/delegation and module namespace manipulation are rejected. The reviewed body import list is
recorded in `own_execution_contract.json`.

These are structural checks with limited routing checks, not complete Python dataflow analysis,
semantic correctness, an arbitrary-code security boundary, or proof of authorship. The immediate tests
and visible experiment still assess behavior when separately executed. Existing third-party libraries
and the configured `python3` kernel remain runtime dependencies; their compatibility and a fresh full
learner run have not been accepted by these source-only checks.

The original course-surface direct detector also expects a particular GPU/publication relation and
legacy marker names. This source pipeline does not claim to make that detector fully green. It does
not add report literals, weaken guards, rewrite historical evidence or award course readiness.
